# RabbitMQ 기반 AI 작업 디스패치 — 구현 계획

설계 정본: [spec.md](./spec.md). 이 문서는 그 설계를 **한 세션에 하나씩 끝낼 수 있는 태스크**로 나눈 것이다.
각 태스크는 자체 완결적이다 — 담당자가 이 문서의 해당 섹션만 읽고 작업할 수 있어야 한다.

---

## Global Constraints

아래는 **모든 태스크에 예외 없이 적용**된다. 태스크마다 다시 확인한다.

### 브랜치 · 베이스

- 베이스 브랜치는 **`develop`**이다. `main`이 아니다. (AGENTS.md: "베이스 브랜치는 항상 `develop`이다.")
- 작업 브랜치: **`feat/rabbitmq-ai-job-dispatch`**
- 시작 전 반드시:
  ```bash
  cd "$(git rev-parse --show-toplevel)"   # 이 저장소(ieum_be) 루트로 이동
  git fetch --all
  git status --short --branch      # 현재 stray 브랜치 chore/inspect-visitor-source-ips-current 확인
  git switch -c feat/rabbitmq-ai-job-dispatch origin/develop
  ```
- ⚠ 현재 워킹 트리는 `origin/main`보다 54파일 뒤처져 있다. **여기서 바로 작업하면 stale 파일 위에 쌓는다.** 위 명령으로 반드시 새로 딴다.
- 큰 태스크를 나눌 필요가 생기면 이슈 브랜치 아래 서브브랜치를 만든다.

### 커밋

- **세부 작업 하나마다 커밋 하나.** 태스크 하나가 커밋 2~3개로 나뉘는 것이 정상이다.
- 형식: **`<type>: <한글 요약>`** — `type` ∈ `feat` | `fix` | `test` | `docs` | `chore` | `refactor`
  - 저장소 실례: `fix: 관리자 콘텐츠 하드삭제 감사 제약 확장`, `feat: 관리자 콘텐츠 하드삭제 추가`, `test: 채팅 공지 저장소 테스트 보강`
- AGENTS.md: "커밋 메시지는 한글로 작성한다. 개략적이되 간결하고 명확해야 한다."
- **★ AI attribution 절대 금지 (예외 없음).** 커밋 메시지·PR 본문·이슈·코드 주석 어디에도 AI 도구를 저자/공동저자로 남기지 않는다.
  - 금지: `Co-Authored-By: Claude ...`, `🤖 Generated with [Claude Code](...)`, `Co-Authored-By: Copilot`, `Generated by ChatGPT`, "Claude가 작성", "AI 생성" — **모든 변형 포함**
  - 도구가 기본으로 붙이려 하면 **제거하고** 커밋한다. author/committer는 항상 실제 사람 계정이어야 한다.
- **커밋·푸시는 사용자가 그 시점에 명시적으로 요청할 때만.** 이전 턴의 허락은 승계되지 않는다.

### TDD

- **RED → GREEN → 리팩터 → 관련 테스트 재실행** 순서를 지킨다. 실패하는 테스트를 **먼저** 쓴다.
- 각 태스크의 "먼저 쓸 테스트" 항목이 RED 단계다. 구현 전에 그 테스트가 **실패하는 것을 눈으로 확인**한다.
- 세부 작업이 끝날 때마다 관련 `memory.md`에 완료 상태·테스트 결과·다음 작업을 기록한다.

### 스키마

- **`spring.jpa.hibernate.ddl-auto=update`를 절대 쓰지 않는다.** 양쪽 앱 모두 `validate` 고정이다. partial unique index·CHECK·enum·geography·vector를 Hibernate가 생성·유지하지 못한다.
- 스키마 SSOT는 **`ieum_be/db/schema.sql`** (git 추적). `code/db/`가 아니다.
- 마이그레이션은 **기존 데이터 보존이 원칙**이다. `DELETE`·`TRUNCATE`·기존 행 값 변경·테이블/컬럼 삭제 금지.
- **H2로는 스키마 검증 불가.** repository·통합 테스트는 반드시 **Testcontainers Postgres**. 순수 단위테스트만 H2/모킹.

### 테스트 실행

```bash
cd "$(git rev-parse --show-toplevel)"   # 이 저장소(ieum_be) 루트로 이동
./gradlew :common:test :app-main:test        # 표준
./gradlew :app-ai:test                       # app-ai 변경 시
./gradlew :app-main:bootJar :app-ai:bootJar  # 빌드 확인
```

- **Docker가 내려가 있으면 Testcontainers 테스트는 전부 `ApplicationContext` 로드 실패로 죽는다. 이때의 실패는 코드 문제가 아니다.** Docker를 올리고 다시 돌린 뒤 판단한다. 특히 신규 `@Query`는 컨텍스트 기동 시 파싱되므로 Docker 없이는 JPQL이 검증되지 않은 상태다.

### ★ Testcontainers 정리 (필수)

테스트 세션이 끝나면 **직접 확인하고 삭제한다.** 컨테이너가 남은 채로 완료를 보고하지 않는다.

```bash
docker ps -a --filter "label=org.testcontainers" --format "{{.ID}}\t{{.Image}}\t{{.Status}}"
docker rm -f $(docker ps -aq --filter "label=org.testcontainers") 2>/dev/null || true
docker volume prune -f
```

- `testcontainers/ryuk` 컨테이너도 함께 확인한다.
- **`docker system prune -a`는 절대 쓰지 않는다** — 같은 호스트의 다른 작업 이미지까지 날린다. 반드시 위처럼 label 필터로 범위를 좁힌다.

### 서버 · 비밀

- **어떤 서버도 시작·중지·변경하지 않는다.** 인프라 태스크(Task 9)는 **저장소 파일 편집만** 한다. 실제 프로비저닝은 운영자가 spec.md §11.3 체크리스트로 별도 수행한다.
- `APP_AI_INTERNAL_CALLBACK_TOKEN`, `RABBITMQ_PASSWORD`, DB 비밀번호 등 **비밀 값을 문서·커밋·CI 로그·PR에 절대 적지 않는다.** 키 이름만 적는다.

### 범위

- 한 번에 한 기능만. 진행 중인 태스크와 무관한 리팩터링·설정 변경은 별도 단위로 분리한다.
- 설계 오버킬 금지. 현재 요구를 충족하는 최소 구조를 택한다.

## Task 3: app-main outbox 쓰기 경로

**목적**: 도메인 트랜잭션 **안에서** outbox row를 만든다. 아직 발행은 하지 않는다.

**파일**

- 생성: `app-main/src/main/java/shinhan/fibri/ieum/main/ai/outbox/entity/AiJobOutbox.java`
- 생성: `app-main/src/main/java/shinhan/fibri/ieum/main/ai/outbox/repository/AiJobOutboxRepository.java`
- 생성: `app-main/src/main/java/shinhan/fibri/ieum/main/ai/outbox/service/AiJobOutboxWriter.java`
- 수정: `app-main/src/main/java/shinhan/fibri/ieum/main/question/service/QuestionService.java` (`create()`, `update()`)
- 수정: `app-main/src/main/java/shinhan/fibri/ieum/main/answer/service/AnswerService.java` (채택 TX, 현 135행 근처)

**먼저 쓸 테스트 (RED)**

- `AiJobOutboxWriterTest` (모킹) — `enqueueQuestionAnswerDispatch(questionId, CREATED)`가 `jobType=question_answer_dispatch`, `routingKey=ai.question-answer.dispatch`, `schemaVersion=1`, 비어있지 않은 `jobId`, `payload`에 `questionId`/`reason` 포함으로 save를 호출. `questionId <= 0` → 예외. `enqueueAcceptedAnswerKnowledge(answerId)` 동상.
- `AiJobOutboxRepositoryTest` (Testcontainers Postgres) — 저장·조회 round-trip. `job_id` 중복 INSERT가 unique 위반. `payload`가 JSONB로 저장되고 원본 JSON과 동등.
- `AiJobOutboxSchemaValidateTest` (Testcontainers Postgres) — `ddl-auto=validate`로 app-main 컨텍스트 기동 성공. **여기서 엔티티/DDL 불일치가 잡힌다.**
- `QuestionServiceOutboxTransactionTest` (Testcontainers Postgres):
  - `create()` 커밋 후 `questions` + `ai_question_tasks` + `ai_job_outbox`가 **모두** 존재하고 outbox row의 `job_key == questionId`, `reason == "created"`
  - 커밋 직전 예외를 주입해 롤백 → **셋 다 없음**
  - `update()`에서 `requestRegeneration`이 `true` → outbox row 1건 (`reason == "regenerated"`)
  - `update()`에서 `requestRegeneration`이 `false` → outbox row **없음**
- `AcceptedAnswerOutboxTransactionTest` (Testcontainers Postgres) — 채택 TX 커밋 시 `job_type=accepted_answer_knowledge_ingest`, `job_key == answerId` row 동반 커밋.

**구현 단계**

1. `AiJobOutbox` 엔티티. spec.md §5.3의 매핑 규칙을 정확히 따른다:
   - `@Table(name = "ai_job_outbox")`, `@Id @GeneratedValue(IDENTITY) @Column(name="outbox_id")`
   - `payload`는 `String` + `@JdbcTypeCode(SqlTypes.JSON)`
   - `status`/`job_type`은 **Postgres enum이 아니므로** `@JdbcType(PostgreSQLEnumJdbcType.class)`를 **쓰지 않는다**
   - 모든 `TIMESTAMPTZ` → `OffsetDateTime`
   - 정적 팩터리 `AiJobOutbox.pending(jobType, jobKey, routingKey, payload)` 제공, 생성자는 `protected`
2. `AiJobOutboxRepository extends JpaRepository<AiJobOutbox, Long>`. 이 태스크에서는 저장만. 클레임 쿼리는 Task 4.
3. `AiJobOutboxWriter` — `ObjectMapper`로 메시지 record를 직렬화해 payload 문자열 생성. `jobId = UUID.randomUUID()`. `@Transactional(propagation = MANDATORY)`로 **호출자 TX 안에서만** 동작하도록 강제한다 (실수로 TX 밖에서 부르면 즉시 실패 — 이게 이 태스크의 핵심 안전장치다).
4. `QuestionService.create()`의 `questionAnswerTicketWriter.create(...)` **바로 다음**에 writer 호출 추가.
5. `QuestionService.update()`의 `if (regenerationRequested)` 블록 **안에** writer 호출 추가 (기존 `eventPublisher.publishEvent`는 **유지** — HTTP 롤백 경로 보존).
6. `AnswerService` 채택 TX에 writer 호출 추가 (기존 `AcceptedHumanAnswerEvent` 발행 **유지**).

> 이 시점에는 아직 릴레이가 없으므로 outbox row가 `pending`으로 쌓이기만 한다. **정상이다.** Task 4에서 소진된다. Task 8의 flag가 기본 `http`이므로 운영에는 영향이 없다 — 단, flag가 `http`일 때 writer가 no-op이 되도록 하는 것은 Task 8에서 배선한다.

## Task 6: 재시도 큐 · DLQ

- `AiJobDeadLetterPublisherTest` (모킹) — `x-death` count `< 5` → NACK 경로 선택. `>= 5` → DLQ republish + **원본 ACK**. `x-ieum-dlq-reason` 헤더 부착. `x-death` 헤더 자체가 없으면 count를 0으로 취급.
- `AiJobRetryDlqIntegrationTest` (Testcontainers RabbitMQ, TTL을 1초로 오버라이드):
  - 컨슈머가 계속 NACK할 때 메시지가 TTL 후 work queue로 **재배달**됨
  - 총 배달 횟수가 정확히 **6회**(최초 1 + 재시도 5)
  - 그 뒤 DLQ에 정확히 **1건** 존재
  - DLQ 메시지에 `x-ieum-dlq-reason`과 `x-death`가 보존됨
  - work queue와 retry queue가 **비어 있음**
- `AiJobImmediateDlqIntegrationTest` (Testcontainers RabbitMQ) — 파싱 불가 본문 1건 발행 → 재시도 **없이** DLQ에 1건 (retry queue를 거치지 않음).

**구현 단계**

1. 양쪽 `AiJobRabbitConfig`/`AiJobRabbitConfiguration`에 spec.md §6.2의 retry 큐 3개 + DLQ 3개 + `ieum.ai.retry`/`ieum.ai.dlx` exchange + 바인딩 6개를 추가한다. **인자는 반드시 `AiJobTopology` 상수에서 가져온다.**
   - work queue: `x-dead-letter-exchange=ieum.ai.retry`, `x-dead-letter-routing-key=<queue>.retry`
   - retry queue: `x-message-ttl=RETRY_TTL_MS`, `x-dead-letter-exchange=<원래 exchange>`, `x-dead-letter-routing-key=<원래 routing key>`
   - DLQ: TTL 없음, DLX 없음
2. `AiJobDeadLetterPublisher` — `message.getMessageProperties().getXDeathHeader()`의 첫 엔트리 `count`를 읽는다. `>= AiJobTopology.MAX_DELIVERY_ATTEMPTS`면 `ieum.ai.dlx`의 해당 DLQ 라우팅 키로 원본을 republish하고 `x-ieum-dlq-reason` 헤더를 붙인 뒤, 호출자가 원본을 ACK하도록 신호한다.
   - **왜 NACK만으로는 DLQ에 못 가는가**: work queue의 `x-dead-letter-*`가 retry queue를 가리키므로 NACK는 항상 retry로 간다. republish + ACK가 유일하게 정확한 방법이다. 이 이유를 Javadoc에 적는다.
3. 리스너 2종에서 정산이 `RETRY`일 때 먼저 `AiJobDeadLetterPublisher`에 상한 도달 여부를 묻고, 도달했으면 DLQ 경로로 전환한다.
4. `requeue=true`를 **어디에도 쓰지 않는다**.

### 배경

현재 app-main은 질문 AI 답변 생성과 채택 답변 지식화를 `RestClient`로 app-ai에 직접 호출한다.
호출이 실패하면 WARN 로그만 남기고 작업이 **영구 유실**된다. 재시도도, 주기 스캔도 없다.
app-ai → app-main 완료 통보도 마찬가지로, 실패하면 `answer_notification_processed_at`이
NULL로 남아 사용자가 AI 답변 알림을 영영 받지 못한다.

DB outbox + RabbitMQ로 옮기면 도메인 커밋과 작업 발행이 원자적이 되고,
app-ai가 내려가 있어도 메시지가 durable queue에 남아 복구 후 처리된다.

### 범위 밖

- 신고 판단(`/ai/v1/internal/reports/{id}/review`)은 동기 request/response RPC이므로 HTTP를 유지한다.
- HTTP 디스패치 엔드포인트 삭제는 별도 후속 이슈로 분리한다(롤백 경로 보존).

## 📢 기능 설명

app-main ↔ app-ai의 AI 작업 디스패치를 HTTP 직결 호출에서 **DB outbox + RabbitMQ**로 옮겼습니다.

**무엇이 바뀌나**

- 질문 AI 답변 생성 / 채택 답변 지식화 디스패치가 메시지 큐를 탑니다.
- 작업 티켓과 발행 이벤트(`ai_job_outbox`)가 **도메인 트랜잭션과 함께 커밋**됩니다.
- 릴레이가 publisher confirms로 발행하고, 실패하면 backoff 재시도합니다.
- app-ai 컨슈머는 manual ACK를 쓰고, 실패 시 30초 TTL 재시도 큐를 5회까지 거친 뒤 DLQ로 격리합니다.
- 질문 완료 통보도 결과 큐로 옮겼고, 재발행 릴레이가 붙어 **알림이 결국 전달**됩니다.

**왜**

기존 경로는 호출 실패 시 WARN 로그만 남기고 작업을 버렸습니다. 재시도도 스캔도 없어서
app-ai가 잠깐만 내려가도 그 사이 등록된 질문의 AI 답변이 영구 유실됐습니다.
완료 통보 실패도 같은 방식으로 사용자 알림을 유실시켰습니다.

**멱등성**

메시지 중복 배달은 기존 `ai_question_tasks` 상태 머신이 흡수합니다.
이미 `completed`인 작업은 LLM을 재실행하지 않고 기존 결과만 다시 흘려보냅니다.
별도 dedupe 테이블을 만들지 않았습니다.

**전환 방식**

`APP_AI_DISPATCH_TRANSPORT=http`(기본값)로 병합되므로 **이 PR 병합 시점의 동작은 현행과 동일**합니다.
브로커 프로비저닝 후 env를 `rabbitmq`로 바꿔 단계적으로 전환합니다. 롤백은 env를 되돌리고 재배포하면 됩니다.
HTTP 엔드포인트는 롤백 경로로 남겨두고 별도 이슈에서 제거합니다.
